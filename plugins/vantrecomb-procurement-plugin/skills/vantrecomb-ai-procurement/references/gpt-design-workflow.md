## Two modes and one versioned design

`one_sentence` translates the buyer's sentence into explicit requirements and edits to the official default/current complete snapshot. Keep official defaults for unspecified fields, identify defaults/unknowns, and ask before a material ambiguous edit. Never invent price, feasibility, certification or a commitment. A covered buyer-requested draft does not need another routine confirmation gate.

`guided` works through the buyer's priorities using the same full schema, including advanced controls and dependencies. Ask the next material question, preserve confirmed choices and the design identity, and save authorized iterations. Modes are interaction styles, not parameter restrictions or automatic RFQ triggers. Preserve the original natural-language `requirements` separately from technical JSON; switching mode can continue the same design.

The source-checked native parameters are:

- `list_designs` reads current owned design summaries; it does not return every full snapshot or select historical versions. Use `read_design` with top-level `id` for the full record. Omit version to read current website/AI work; `query.version` selects a positive historical version. Query values are strings in the MCP schema, for example `{"version":"2"}`. Do not assume the last chat snapshot is current.
- `create_design` uses top-level `payload` containing all of `sku`, `base_version=0`, complete v2 `snapshot`, original `requirements` string, and `mode=one_sentence|guided`, plus a required top-level `idempotency_key`. Start from `design_capabilities.snapshot`, not a fabricated initial design ID or partial JSON.
- `update_design` uses top-level `id` and `idempotency_key`, and the same complete `payload` shape with the current observed `base_version`. Read current full snapshot/version before updating, including after webpage changes. Apply only the authorized delta, preserving unmentioned advanced fields/assets/requirements. Retain the same design ID; it cannot move to another SKU/template. A different product requires a separately authorized new design, not silently rebinding the old ID.

Successful save records return `design_id`, `version`, `sku`, `template_id`, `snapshot`, `requirements`, `mode`, `updated_at`, `preview_url`. Trust those returned identifiers/versions, and report save success only from success. Versions are immutable; website saves create new private versions readable by AI on the same design ID. A saved/previewed draft is not an ERP-approved production plan, an RFQ or an amendment to an old quote.

All design write calls require an `idempotency_key` (candidate schema maximum 128 characters). Keep the same key for a retry of the identical account/action/payload; a changed payload or operation needs a new key. `409 idempotency_payload_conflict` is not a version conflict: do not reuse that key for changed data or create duplicate business submissions to hide uncertain completion. Durable receipts support identical retries after response loss/restart, subject to current authorization.

## Logo input and the same-design website fallback

`upload_design_logo` requires top-level `design_id` for an owned saved design and `idempotency_key`. Save first if necessary. Its optional top-level `file` is identified by `_meta["openai/fileParams"]=["file"]`; within it `download_url` and `file_id` are required, `mime_type` and `file_name` optional, and extra fields forbidden. Pass only the supported attachment object supplied by the host, never invent a file ID/URL or turn a pasted external link into an official file.

The candidate `customer_upload_policy` exposes the exact limits and forbids vector/relief uploads and ERP review. Current validation accepts static PNG/JPEG/WebP, maximum 512 KiB, maximum side 2048, plus decoded-pixel/byte checks; inspect the current returned policy for all bounds. This is design artwork, not a general quote/payment/customer-document upload API.

Attachment ingress defaults disabled with empty `PROCUREMENT_DESIGN_ATTACHMENT_HOSTS`. Only separately approved exact HTTPS hostnames on port 443 are accepted; no wildcards, suffix matching, redirects, proxies, URL credentials or account-credential forwarding. Host/DNS/address/time/byte controls are enforced by the provider. The official file-input shape does not approve a hostname. Exact host approval and real GPT attachment import remain pending; do not enable domains, make direct downloads or promise upload support from the annotation alone.

Without a host file, or when ingress is disabled, the tool returns `upload_mode=website` and the owned design's `website_upload_entry` with `mode=edit`. Share that actual entry, preserving design/version; do not construct another route. It is fallback, not completed upload. The buyer uploads/edits on the website; then read the latest design before further AI changes. Browser positive completion is still CSP-blocked, so disclose that limitation instead of promising the fallback works end to end.

Successful asset upload returns `asset_id` and a canonical account-private `resource` (`dasset_…`, `/api/v1/ai/me/design-assets/dasset_…`, kind/logo label), plus image metadata. It does not automatically attach artwork or create a design version: use the returned canonical resource in the complete snapshot's actual supported artwork fields and save an authorized update. Temporary ChatGPT URLs/file IDs are not persistent design resources and must not be placed in snapshots or shared/logged. Other accounts cannot read the private bytes (404); upload does not grant public sharing.
