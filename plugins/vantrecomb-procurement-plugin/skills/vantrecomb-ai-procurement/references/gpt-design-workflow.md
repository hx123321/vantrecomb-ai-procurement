## Two modes and one versioned design

`one_sentence` translates the buyer's sentence into explicit requirements and edits to the official default/current complete snapshot. Keep official defaults for unspecified fields, identify defaults/unknowns, and ask before a material ambiguous edit. Never invent price, feasibility, certification or a commitment. A covered buyer-requested draft does not need another routine confirmation gate.

`guided` works through the buyer's priorities using the same full schema, including advanced controls and dependencies. Ask the next material question, preserve confirmed choices and the design identity, and save authorized iterations. Modes are interaction styles, not parameter restrictions or automatic RFQ triggers. Preserve the original natural-language `requirements` separately from technical JSON; switching mode can continue the same design.

The merged-source native parameters are:

- `list_designs` reads current owned design summaries; it does not return every full snapshot or select historical versions. Use `read_design` with top-level `id` for the full record. Omit version to read current website/AI work; `query.version` selects a positive historical version. Query values are strings in the MCP schema, for example `{"version":"2"}`. Do not assume the last chat snapshot is current.
- `create_design` uses top-level `payload` containing all of `sku`, `base_version=0`, complete v2 `snapshot`, original `requirements` string, and `mode=one_sentence|guided`, plus a required top-level `idempotency_key`. Start from `design_capabilities.snapshot`, not a fabricated initial design ID or partial JSON.
- `update_design` uses top-level `id` and `idempotency_key`, and the same complete `payload` shape with the current observed `base_version`. Read current full snapshot/version before updating, including after webpage changes. Apply only the authorized delta, preserving unmentioned advanced fields/assets/requirements. Retain the same design ID; it cannot move to another SKU/template. A different product requires a separately authorized new design, not silently rebinding the old ID.

Successful save records return `design_id`, `version`, `sku`, `template_id`, `snapshot`, `requirements`, `mode`, `updated_at`, `preview_url`. Trust those returned identifiers/versions, and report save success only from success. Versions are immutable; website saves create new private versions readable by AI on the same design ID. A saved/previewed draft is not an ERP-approved production plan, an RFQ or an amendment to an old quote.

All design write calls require an `idempotency_key` (reviewed schema maximum 128 characters). Keep the same key for an identical account/action/payload retry; changed business data or operation needs a new key. Official Logo retries are the specific exception for a refreshed temporary URL: stable file identity/metadata and design remain identical, so keep the same key as described below. `409 idempotency_payload_conflict` is not a version conflict: do not reuse that key for changed data or create duplicate business submissions to hide uncertain completion. Durable receipts support identical retries after response loss/restart, subject to current authorization.

## Field validation and concurrent webpage edits

Validation is deep and strict: the producer-derived schema checks nested types, required fields, enums, array items and unknown fields, including artwork/resources and optional advanced design. The original import/resolver/compiler then checks canonical advanced/layout/recipe ranges and legal packaging layers, materials, capacities, closures and real printable surfaces. Follow actual field rules and combinations, not just top-level JSON validity. The reviewed worker accepts only the customer client target, never ERP/development targets. Do not treat packaging review ranges as hard min/max bounds or remove unknown/invalid values silently.

For templates with a formal recipe, the final worker always checks saved length/width/thickness against the original `dimensionRange(axis)` and formal producer recipe baseline, with or without optional advanced design. The returned field_table projects the resulting mm limits for top-level and recipe dimensions; do not substitute a caller-edited baseline/bounding box or merely make both copies equal. A dimensions error can precisely identify `extensions.photoRecipe.parameters.dimensionsMm.length` (or width/thickness). If `extensions.photoRecipe.design` is present, its original compiler output must also match saved dimensions. Keep authorized changes consistent with that producer-derived design and returned ranges; do not delete design, copy a stale scale, change two fields together or clamp defaults to evade the checks. This source validation/persistence is not evidence of a real advanced geometry → Blender rebuild → changed preview loop.

MCP failures can arrive as `isError=true` text such as `API_HTTP_422: {...}` or `API_HTTP_409: {...}`; use the actual status/code/fields in that result, not an assumption that every tool failure is an HTTP response. For `422 fields`, read actual paths/reasons and the authoritative constraints. Explain what failed, correct only supported changes within the buyer's intent and preserve unrelated data. Ask about a material choice; do not clamp/coerce, replace illegal values with defaults or remove unknown nested data to force a save. A rejected snapshot was not saved. `404 design_not_found` or private asset 404 must not trigger another-account fallback. `503 design_validator_unavailable` / `design_storage_unavailable` means the provider could not validate/store, not that a default snapshot would solve it; report and retry only safely. `422 invalid_design_artwork` / `too_many_design_assets` requires fixing authorized referenced artwork rather than assuming a new version was saved. `403 account_contact_mismatch` belongs to RFQ identity/contact correction below. For uncertain RFQ completion such as `quote_commit_uncertain`, follow the returned same-key recovery instruction; do not change the key and submit again. Schema-level malformed requests may return `400 invalid_design_request`; fix the actual payload shape rather than retrying it unchanged.

For `409 design_version_conflict`, read the latest record and, if useful, the requested historical version. Merge the buyer's intended delta into the current complete snapshot, then retry with its observed base_version and a new key for the changed payload. If both parties changed the same field or the merge would discard a customer's webpage edit, explain and ask before retrying. Do not force overwrite, resend stale snapshots, create replacement designs to hide conflicts or loop indefinitely.

## Logo input and the same-design website fallback

Missing `design_id`/key or malformed file gives `design_id_required`, `idempotency_key_required` or `invalid_host_file`; attachment URL/host/MIME/address failures are tool errors such as `attachment_host_not_approved`, `attachment_unavailable`, `attachment_mime_mismatch`, not completed upload.
