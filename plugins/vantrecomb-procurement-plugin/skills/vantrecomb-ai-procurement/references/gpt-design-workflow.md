## Two modes and one versioned design

`one_sentence` translates the buyer's sentence into explicit requirements and edits to the official default/current complete snapshot. Keep official defaults for unspecified fields, identify defaults/unknowns, and ask before a material ambiguous edit. Never invent price, feasibility, certification or a commitment. A covered buyer-requested draft does not need another routine confirmation gate.

`guided` works through the buyer's priorities using the same full schema, including advanced controls and dependencies. Ask the next material question, preserve confirmed choices and the design identity, and save authorized iterations. Modes are interaction styles, not parameter restrictions or automatic RFQ triggers. Preserve the original natural-language `requirements` separately from technical JSON; switching mode can continue the same design.

The source-checked native parameters are:

- `list_designs` reads current owned design summaries; it does not return every full snapshot or select historical versions. Use `read_design` with top-level `id` for the full record. Omit version to read current website/AI work; `query.version` selects a positive historical version. Query values are strings in the MCP schema, for example `{"version":"2"}`. Do not assume the last chat snapshot is current.
- `create_design` uses top-level `payload` containing all of `sku`, `base_version=0`, complete v2 `snapshot`, original `requirements` string, and `mode=one_sentence|guided`, plus a required top-level `idempotency_key`. Start from `design_capabilities.snapshot`, not a fabricated initial design ID or partial JSON.
- `update_design` uses top-level `id` and `idempotency_key`, and the same complete `payload` shape with the current observed `base_version`. Read current full snapshot/version before updating, including after webpage changes. Apply only the authorized delta, preserving unmentioned advanced fields/assets/requirements. Retain the same design ID; it cannot move to another SKU/template. A different product requires a separately authorized new design, not silently rebinding the old ID.

Successful save records return `design_id`, `version`, `sku`, `template_id`, `snapshot`, `requirements`, `mode`, `updated_at`, `preview_url`. Trust those returned identifiers/versions, and report save success only from success. Versions are immutable; website saves create new private versions readable by AI on the same design ID. A saved/previewed draft is not an ERP-approved production plan, an RFQ or an amendment to an old quote.

All design write calls require an `idempotency_key` (candidate schema maximum 128 characters). Keep the same key for an identical account/action/payload retry; changed business data or operation needs a new key. Official Logo retries are the specific exception for a refreshed temporary URL: stable file identity/metadata and design remain identical, so keep the same key as described below. `409 idempotency_payload_conflict` is not a version conflict: do not reuse that key for changed data or create duplicate business submissions to hide uncertain completion.
