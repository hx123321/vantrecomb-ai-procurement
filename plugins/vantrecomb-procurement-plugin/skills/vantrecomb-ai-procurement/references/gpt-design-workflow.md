# GPT customer 3D customization — candidate contract

This chapter prepares the user-approved GPT workflow: native tools, customer Logo upload and an existing private 3D preview link first; an embedded chat UI later. The core website/3D work is still coordinated WIP. Tool names, arguments, responses, authoritative rule sources, scopes and feature configuration below are **candidate expectations supplied by the parent, not a reviewed/merged API or live availability claim**. Before releasing this skill, reconcile them with the final core PR's actual schema, validator and mechanism documentation. When tools are missing or differ, report the limitation and stop dependent calls; never infer REST routes or silently use another account.

## Discover the actual parameter contract

For the selected product, inspect the native `design_capabilities` schema and, if the matching capability is available, request `query.sku` using an actual catalog SKU. Read the returned formal rules, complete default v2 snapshot and Chinese field explanations. Treat the official customer-facing JSON and validator as the authority for parameter paths, types, units, enum values, ranges, defaults, dependencies and customer editing restrictions. If a property is absent, do not invent its path, range, unit, enum or support. Refresh capabilities when the SKU or returned rule version changes.

Give the buyer the exact authoritative parameter JSON and its returned field explanations when requested. A concise table may be generated directly from that response using the actual field path, Chinese label/meaning, type/unit, allowed range or choices, default and dependency/restriction **only when supplied**. Keep advanced fields and nested recipe/contour fields visible; do not reduce it to a hand-picked basic subset. This presentation must not become a bundled copied JSON schema, a second capability table or an AI-maintained list of allowed values. If the capability result is missing a needed explanation/constraint, disclose the gap and wait for the actual contract; do not fill it from memory or narrative website copy.

The scope of customer customization must cover the current customer configurator's full supported options for the chosen SKU: materials and dimensions; segmented comb teeth; brush pins, bristles/planting and cushion; assembly and component colors; advanced recipe/local contour; Logo/full-color patterns and process grades; surface treatments; and all supported packaging. These are coverage goals, not invented JSON field names or universal SKU permissions. Use authoritative applicability/dependency rules for each family. ERP review/internal settings and customer-disabled vector/relief upload remain unavailable, even if internal source data mentions them. Do not equate an allowed process selection with permission to upload its prohibited asset type.

## Two modes, one persistent design

In `one_sentence` mode, translate the buyer's sentence into explicit requirements and edits to the returned complete default/current snapshot. Preserve official defaults for unspecified fields, say which values are defaults and mark unresolved requirements; never invent price, feasibility, certification or a commitment. A buyer-requested draft can be saved under effective authorization without adding a routine confirmation gate. Material ambiguity that changes the design needs clarification before the dependent edit.

In `guided` mode, work through the buyer's priorities using the same complete parameter contract. Explain dependent choices, including advanced controls, rather than restricting them to basic fields. Ask only the next material question, retain confirmed choices and the same design identity, and save authorized iterations when enough information is available. Modes are interaction styles, not different parameter capabilities or automatic RFQ triggers. Switching mode should continue the same design using the actual schema.

The candidate native workflow is:

- `list_designs` / `read_design`: read buyer-owned saved designs; use `query.version` only as supported by the final schema for a requested version. Otherwise read the current design before edits, including after customer website changes. Do not assume the last chat snapshot is still current.
- `create_design`: create the requested design using actual `sku`, complete v2 `snapshot`, `requirements`, and `mode=one_sentence|guided`. Use the actual schema's remaining parameters, ownership/scopes and required idempotency behavior; do not fabricate a design ID or an initial `base_version`.
- `update_design`: retain the same returned `design_id`, read the current snapshot/version, apply only the buyer's requested changes to a copy, preserve unmentioned advanced fields/assets/requirements, and submit the complete v2 snapshot plus the required observed `base_version` optimistic lock. Use the actual schema for SKU/requirements/mode and any required key. Do not send an assumed partial patch or create a replacement design for each message.

Store only returned design identifiers and versions needed for the conversation, not credentials. Report a save as successful only from a successful tool result and its actual returned version. A saved/previewed design is a customer design version, not an ERP-approved production plan or an amendment to an old quote. Do not overwrite ERP proposals or prior quotations.

## Validation and concurrent website edits

For candidate `422` validation failures, read the returned `fields` paths/reasons and current authoritative constraints. Explain the rejected fields in plain language. Correct only supported changes covered by the buyer's intent; ask about a material choice instead of silently substituting a design. Preserve unrelated fields. Do not guess coercions, clamp values, remove unknown nested data to make validation pass, or say the rejected version was saved.

For candidate `409 design_version_conflict`, read the latest design/version and any supported explicitly requested version. Compare the current website design with the buyer's intended edit, merge only that edit into the current full snapshot, and retry with the newly observed `base_version` when authorization still covers it. If both sides changed the same field or the result would discard a customer edit, explain the conflicting choice and ask before retrying. Never force overwrite, blindly resend a stale snapshot/version, or restart as a new design to hide the conflict. Customer webpage edits remain readable for the next AI iteration through the same design ID. Repeated conflicts should be reported instead of looping indefinitely.

## Logo upload and private preview fallback

The candidate `upload_design_logo` always needs an actual saved `design_id`; save the design first if necessary. Attach a file only through the final tool's official `openai/fileParams` / `file` capability when the host actually supplies a supported attachment. Follow the returned/schema MIME, size, asset-type and ownership restrictions. This is a design Logo channel, not a general quote/payment/customer-document upload API. Customer-disabled vector/relief uploads and ERP internal review are not opened by it.

Attachment reception and exact trusted HTTPS file-source configuration are pending. Do not claim real GPT attachment upload works, accept arbitrary URL downloads, invent a file handle, copy secrets from signed URLs or use a random external file service. If the host cannot pass an attachment, use the native no-attachment fallback only when actually exposed: it returns a website upload entry for the **same design**. Give that returned entry as-is; do not construct a route. After the buyer uploads on the website, read the current design/version again before further edits. A missing file/fallback response is a limitation, not successful upload.

The save candidate returns a private `preview_url` for `/designs/preview?design_id=…&version=…`. Share the actual provider-returned absolute URL; if the live contract returns a relative URL, resolve it only against the verified configured website origin. Do not invent design IDs, versions or hosts. Retain the returned version when describing a saved preview; a later website edit can create a newer version that must be read back. The URL is a private existing webpage, not public sharing authorization, an automatically rendered iframe or a chat-native 3D widget. Respect the website's normal login/ownership rules and use the existing independent/incognito SSO guidance when the host supports and exposes it. Do not reuse the buyer's original context with another account.

An ordinary link remains a link. Embedded chat 3D controls require the later MCP Apps UI integration and host support, neither delivered nor verified by this draft. If a preview is unavailable, report the saved design ID/version and the actual returned website entry or limitation; do not generate an unrelated mock model and call it the customer's saved design.

## Explicit RFQ submission and authorization boundary

Save, Logo upload and preview do not automatically submit an inquiry or quote. The candidate `submit_design_rfq` explicitly selects a saved `design_id` and version, quantity and contact details, reusing the existing RFQ/quotation flow. Read that exact design version and summarize it with the actual submitted business payload. Execute only when the buyer's explicit confirmation covers that version, quantity and contact data and the final tool's confirmation/idempotency/validation requirements are met. A design request, ordinary website permission, preview click or previous confirmation of another version is not submission approval. Report the actual returned RFQ/quote reference rather than claiming sales acceptance or a price.

New `me:designs:read` / `me:designs:write` and TEST feature enablement require the parent's concrete approval and final scope contract. They are not currently approved or deployed capabilities in this draft. Old grants do not automatically gain them; missing scopes must use supported genuine host reauthorization, never grant edits or website credentials to bypass plugin API checks. Native tool discovery governs availability; normal website session permissions do not authorize AI to perform unrequested business writes.
