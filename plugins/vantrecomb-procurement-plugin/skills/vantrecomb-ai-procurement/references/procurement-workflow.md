## Buyer-requested pre-order inquiry abandonment

Read the owned quote using the actual exposed read tool and required scope before deciding. After matching deployment, [the merged MCP schema](https://github.com/hx123321/vantreCombB2B/blob/e99108c22a5efb11d46fa26f6e77b6a19f2a0d71/backend/cmd/server/mcp_procurement.go) extends existing `respond_quote` with `action=abandon`; it does not add a separate abandonment tool. Required top-level arguments are `id`, `action`, `payload`, `buyer_confirmed=true` and `idempotency_key`. The scope is `me:quotes:respond`, with current account and quote ownership checked on calls and receipt recovery. Do not invoke a REST route if the host schema does not yet expose this action.

Put the buyer's nonblank reason in `payload.note` (trimmed, at most 2000 Unicode characters); `reason` is not the request field. Do not invent a reason or require acceptance contact fields for abandonment. Optional supported `payload.contact` and `payload.client_request_id` must follow the current contract; if the latter is supplied, it must equal the top-level key, forwarded as `Idempotency-Key`. Use a nonblank key of at most 128 printable ASCII characters without spaces. No password setting or attachment upload belongs in this action.

The buyer may proactively abandon only before confirmed order intent and with no linked order. Read returned `can_abandon`, current actions and order relationship; the [server lifecycle guard](https://github.com/hx123321/vantreCombB2B/blob/e99108c22a5efb11d46fa26f6e77b6a19f2a0d71/backend/cmd/server/quote_lifecycle.go) is authoritative. An earlier order confirmation blocks abandonment even before an ERP order number appears. Do not copy a static status allowlist or decide from a label alone. Show the exact inquiry, reason and effect, and require effective explicit buyer confirmation covering that payload before setting `buyer_confirmed=true`.

Success returns the current quote projection with HTTP 202 under the underlying contract: the inquiry closes immediately, active inquiry quota is released, all history/first closure decision is preserved, and the response is queued for ERP checks. Read the owned quote back after success and report its actual closed state and retained receipt. Do not describe a pending ERP check as complete. No order, production or payment is cancelled or changed by this operation; order cancellation still uses the existing salesperson follow-up.

For an uncertain result or lost response, read current state and retry the identical target/action/normalized reason/contact with the same key when authorized. The retained receipt deduplicates the retry across normal restart without requeueing or a second audit event. A repeat click on a previously abandoned closed inquiry retains the first decision; do not create a new key to rewrite its reason. On any 409, read the current quote first. `QUOTE_ACTION_CONFLICT` may mean confirmed order intent or an order link; stop abandonment. `IDEMPOTENCY_CONFLICT` means the key's payload changed; reconcile the original receipt and intended action rather than forcing a fresh duplicate. A changed legitimate payload requires a new key and appropriate buyer authorization. Missing scope/authentication or 404 ownership remains a boundary, never permission to switch credentials or call another account.

General quotation/payment/customer documents have no upload API. The deployed design-specific Logo channel is described separately in `gpt-design-workflow.md`; direct GPT attachment ingress remains disabled, and this channel does not authorize general upload. Drawings, payment evidence, and other buyer-provided files must be emailed to the assigned salesperson. Once a quote record exists, read its top-level `sales_contact.email`; use the quote message endpoint when an auditable site-side conversation is preferable.

For files generated by ERP or configured on the site, check the buyer's email first because sales normally sends them there. If the email or attachment is missing, use `list_documents` and authorized `document_link` with its required `idempotency_key`. The result has `delivery_mode=caller_ip_bound`: the temporary API `download_url` is bound to the caller's IP and must not be directly followed or forwarded as a buyer-browser download link. Give the buyer the actual returned `website_download_entry`, where they sign in and use the existing controlled download flow. Do not invent that URL, promise cross-browser use of the temporary URL, or claim the file was retrieved or attached. The MCP tool does not fetch, attach or stream bytes and provides no upload capability.

Use `PATCH /api/v1/ai/me/profile` only for default contact/address details. The site does not expose direct order cancellation, order-specific address changes, or after-sales state transitions to AI. For those requests, send `POST /api/v1/ai/me/quotes/{quote_id}/messages` and wait for the assigned salesperson's reply before reporting completion.

Cloud plugins use only the verified host-managed OAuth connection and its actual exposed tools. Local clients are for separately requested local workflows with independently verified server/client configuration; their Device Authorization implementation does not establish current server support. A failed cloud connection, 401/403, missing scope or denied ownership must not trigger local API, manual-token or browser-session fallback. All authorized local POST/PATCH commands still require buyer confirmation and an idempotency key.

Subsequent pages, reads/writes, downloads, refresh and logout follow the original website chain. Website expiry/logout does not revoke the plugin grant; valid plugin authorization permits a new handoff without repeating consent. Plugin revocation prevents new handoffs but does not log out an established website session or stop its normal refresh. End that login with its normal website logout in the chosen context.

OAuth access/refresh never reach browser JS, localStorage or URLs. The website itself handles its ordinary short access and refresh cookie as in manual login.
