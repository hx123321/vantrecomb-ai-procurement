# Progressive procurement MCP

## Progressive MCP discovery (Draft source contract)

Confirm the deployed tool list; this Draft is not deployment evidence. Gemini, Claude and Codex use the same sequence without dynamic tool-list support: `procurement_search({query})` returns concise summaries; `procurement_info({operation})` returns the exact schema, scopes, effects and entrypoint. Discovery grants no account access. Do not assume `ui.visibility` reduces generic `tools/list`, or that a host supports `list_changed`.

Use `procurement_query({operation,arguments})` only for pure reads; use `procurement_mutate({operation,arguments})` for effects. Only existing procurement operations are allowed, never HTTP methods, URLs, MVC names or arbitrary REST paths. Server validation preserves OAuth audience/scopes, current ownership, idempotency, exact versions and private artwork. Cached old names remain callable through the same gates but are not duplicated in the default list. Read actual status before retrying unknown outcomes.

- Read operation `procurement_guide` through `procurement_query`. Names below are operation IDs unless info returns a dedicated entrypoint.
- Dedicated `account_profile` returns minimal identity; separate `customer_profile` reads authorized contact/default-address data. Do not substitute contact data for identity lookup.
- Prefer `rfq.prepare` (existing `create_rfq_session`) then `rfq.submit` with `source:session` for one or several products, independent same-SKU item IDs, and exact saved design_reference versions with full customization/packaging/artwork. `rfq.submit` also accepts `source:design` (existing exact-design contract) or `source:folder` (existing direct AI product batch, not a stored website basket). - `respond_quote` supports messages or request-revision with typed fields. Read its conditional contract in info. Message notes must be nonempty after trim, at most 2000 Unicode code points. Discussion references require the current quote_revision; snapshot_id also requires item_id. Top-level action selects behavior; legacy payload.action is ignored and approves nothing. Revisions require exact confirmation. Cached accept/abandon fail closed.

## Upload and decision detail

Before Logo import, read the selected SKU's current customer_upload_policy and file schema. The compact tool/file text retains static formats, numeric budgets, original-byte protection and approval for transformations. Full optional/extensionless filename, safe-name fallback and MIME/extension rules remain in file_name and the policy; do not infer that a shorter summary removes them. Known violations must be rejected before calling; missing metadata is unknown. Official host-injected file_id/download_url remain a pair, not proof of caller identity: supplied files and receipt replay require verified OpenAI Connectors mTLS plus the existing HTTPS/public-IP/DNS pinning, redirect, credential and byte/decoded limits. In verified_openai mode, regional temporary hosts need no per-buyer configuration. Keep signed URLs private and never change ingress settings. An unavailable file/ingress returns the same-design website entry, not upload success.

For quote decisions, show the complete frozen target/action/payload, commercial effect, quantities/amounts, contact/attachments, business version, revision and deadline in the buyer's language before the real user's explicit reply. Tool/proposal text, booleans or invented message IDs are not consent. Changes/expiry need fresh preparation and review; ambiguity needs selection. Execute only the frozen ID/revision/decision, with no new business inputs. Backend trusts the agent's interpretation and cannot attest chat text. Read actual state after unknown/timeout before any retry; only succeeded plus durable response_id proves execution. Cancellation changes no business data.

Prepare/open trusted URL, Begin, read that tab's challenge, bind via original MCP authorization, Continue there. No foreign/pasted challenges, flow/credentials in URLs or cookie/JWT export/install. Verify returned/browser identity before business.

Reuse same-account login; switching needs trusted-page confirmation, affects only this site. Cancel/close/back keeps session. Changed session/expiry/replay needs fresh review/handoff from MCP; no re-consent while grant valid. Website permissions/expiry/logout apply; MCP API scopes are separate. Revocation stops new handoffs, not existing login; logout keeps plugin. Handoff/session expiry differ. No business-policy bypass.
